# Task brief for the session on the 4080 workstation

This file is the hand-off. It is written for a Claude Code session running on
the user's local workstation (two RTX 4080, 16 GB each), which does NOT share a
filesystem with the TACC Lonestar6 session that produced the work. Pull this
file for updates (`git pull` inside the kit's `code/pmp-s3denergy`) — it is the
authoritative version, the copy inside the kit snapshot may be older.

## What you have

A self-contained kit, `mini_kit_4080/`, 2.5 GB, 653 files, copied by hand from
Lonestar6. `sha256sum -c MANIFEST.sha256` passed on the source machine. It
holds two frames of the 800-frame NiN dataset with everything needed to run
single-frame diagnostics of a residual-3D solvent-charge model:

- `dft/1-44_GCE/cal_1` — sid 1, NiN44 at q = -1.00 (charged)
- `dft/5-44_neutral_withsolv/cal_1` — sid 601, the same geometry, neutral
- `run/` — checkpoints, per-sid sliced caches, the two-frame xyz, PB config
- `audits/` — 24 diagnostic scripts, absolute paths replaced by env vars
- `code/` — both repos as working trees plus verifiable git bundles

## Non-negotiable constraints

1. **float64 everywhere in the PB path.** `cep-dip-python-pb/pure_python/torch_pb.py`
   line 20: "float64 by default to clear the cal_18 validation gate; float32
   diverges on this ill-conditioned problem". Do not switch to float32 to gain
   speed, and do not add autocast. A 4080 runs float64 at 1/64 of its float32
   rate (an A100 does 1/2), so these runs are slow by design.
2. **Do not run anything involving sid 201 (NiN88).** The joint-fit Gram matrix
   for that cell is 36612 x 36612 in float64 = 10.7 GB for one matrix and it
   already hit OOM on a 40 GB A100. It will not fit in 16 GB.
3. **No training, no fine-tuning.** Needs 40 GB class memory; the two cards
   have no NVLink and the scripts are single-GPU.
4. Report numbers, never verdicts alone. Every reported result carries the
   actual figures (this is a standing instruction from the user: "一切结果汇报
   都要具体数字，不许只说'过了/没过'").

## Step 1 — verify the kit before trusting anything

```bash
cd mini_kit_4080
sha256sum -c MANIFEST.sha256 --quiet   # must print nothing
source env.sh
cd run
python -u smoke_test.py 2>&1 | tee smoke_local.log
```

`smoke_test.py` measures float64 DGEMM and float64 FFT at two grid sizes on
this card, then runs the forward pass for sid 1 and sid 601 and compares every
solvent energy term against `reference_values.json`, which was generated by the
same code on an A100. Tolerance is 1e-6 relative.

- `SMOKE PASS` — the port is numerically equivalent; go on.
- `SMOKE FAIL` — stop. Report which term differs and by how much. Do not run
  the diagnostics; their results would be meaningless.
- If `reference_values.json` is absent, the comparison cannot run. Report the
  measured values and the benchmark anyway; the reference is generated by a
  queued Lonestar6 job and can be added later.

Environment versions must match: torch 2.2.1 + cu121 (its wheels include
sm_89, so a 4080 works without building anything), ase 3.22.1, e3nn 0.4.4,
scipy 1.13.1. Full list: `code/pmp-s3denergy/requirements-freeze.txt`.

## Step 2 — the diagnostic that is actually wanted

The open scientific question: the model's 3-D residual solvent charge recovers
too little of the lateral (in-plane) solvent response, and it is not yet known
whether that is because the predicted cavity is wrong or because the
representation cannot express what is needed.

Run, from `run/`:

```bash
python -u ../audits/cavity_compare.py 2>&1 | tee cav_local.log
```

Two definitions must not be mixed up when reading its output, and this is the
single most important thing in this brief:

- **raw solvent charge** = RHOB + RHOION, converted to a density. This is a
  physical quantity. "Is there solvent here?" is a question about this.
- **lateral charge** = raw minus its xy-plane average, `rho - <rho>_xy`. This
  is a decomposition. Even where the raw charge is exactly zero, the lateral
  part is non-zero, equal to `-<rho>(z)`, purely cancelling the plane average.

So a non-zero lateral residual inside a closed cavity is NOT evidence that
solvent is there. An earlier reading of exactly this kind ("28.5% of the
lateral charge sits where the cavity is closed, therefore the cavity is wrong")
was retracted. The script now reports the two separately: `[Q1-raw]`,
`[Q1-lateral]`, `[Q1-dist]`, `[Q2]`, `[Q2-raw]`, `[Q3]`.

What to extract from the output, in order of importance:

1. From `[Q2-raw]`, for each of the four cavity classes (both open / both
   closed / model CLOSED DFT open / model open DFT CLOSED): the true raw net
   and absolute charge, the model's broadcast 1-D background, the residual
   amplitude, and both cross energies. The discriminator is:
   - significant **raw** charge in "model CLOSED, DFT open" → the cavity
     prediction is wrong;
   - raw net charge near zero while the background is not, with a small
     residual amplitude → a representation defect: the model spreads its 1-D
     background over the whole z-plane including inside the solute, while the
     envelope forbids the 3-D residual from cancelling it there. This one is
     independent of whether the cavity is correct.
2. From `[Q1-raw]`: how RHOB distributes against s_diel and RHOION against
   s_ion. Report the distribution, do not assert anything from it — VASPsol++
   bound charge is -div P with a non-local convolution, so it is not required
   to vanish where s_diel is small.
3. From `[Q1-dist]`: the distance-to-nearest-atom binning on the native DFT
   grid (168 x 168 x 500), raw and lateral side by side. This exists to check
   whether an earlier claim ("90% of the lateral charge within 1.5 A of a
   solute atom") was an interpolation artifact of the coarser model grid
   (100 x 100 x 300).
4. From `[Q3]`: the density comparison, plus the caveat the script prints —
   the DFT density is put through the MODEL's cavity parameters, so it isolates
   the effect of the density input and cannot by itself rule out a recipe or
   parameter mismatch.

If `[Q1-dist]` reports a memory failure it is guarded and skipped; lower the
`4.0e7` chunk constant in `cavity_compare.py` and rerun. Nothing else in the
output depends on it.
